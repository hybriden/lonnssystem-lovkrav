## Mål

Pakken gir alle senere pakker ett mønster for endepunkter: hvordan et endepunkt registreres, validerer input, autoriserer, kaller domenet, og svarer. Den setter opp OpenAPI-dokumentet og genererer TypeScript-klienten til `web/`, så API og frontend ikke drifter.

## Omfang

- `Program.cs` med lagdelt oppsett: konfigurasjon, logging (strukturert, uten personopplysninger), autentisering fra AP-006, `LonnDbContext` fra AP-005, OpenAPI.
- Endepunktgrupper per domeneområde som `IEndpointGroup`-implementasjoner, oppdaget automatisk, med felles filter for autorisasjon og `IArbeidsgiverKontekst` fra ruten `/api/arbeidsgivere/{arbeidsgiverId}/...`.
- Feilmodell: RFC 9457 Problem Details for alle feil. Valideringsfeil 400 med felt og kode. Domenefeil (fra `Result<T, Feil>`) mappes til 400, 404, 409 eller 422 etter feiltype. Uventede feil gir 500 uten detaljer og med en korrelasjons-ID som også logges.
- Input-validering med `FluentValidation` eller DataAnnotations (velg én, dokumenter); ugyldig input gir aldri 500.
- Svar: `{ data: ... }` for ett objekt, `{ data: [...], total }` for lister med sidevisning (`side`, `storrelse`, maks 200).
- JSON: camelCase, `DateOnly` som `YYYY-MM-DD`, `decimal` som tall med to desimaler (ikke streng), strengkoder for kodelister (ingen enum-tall).
- OpenAPI 3.1 med `Microsoft.AspNetCore.OpenApi`, eksempler per endepunkt, og en CI-sjekk som feiler om dokumentet har endret seg uten at den innsjekkede kopien i `web/src/api/openapi.json` er oppdatert.
- Klientgenerering til `web/src/api/client.ts` med `openapi-typescript` og `openapi-fetch`. Script `pnpm run api:generate` (eller `npm`) i `web/`.
- Helsesjekk `/health` (uten autentisering, uten databaseinnhold) og `/health/ready` (sjekker database).
- Ett eksempelendepunkt `GET /api/arbeidsgivere/{id}` med alt over, som mal.

## Utenfor omfang

- Alle domeneendepunkter (fase 1 og utover).
- Frontend-oppsett (AP-008).
- Ratebegrensning og autentisering (AP-006).

## Regler

- Fødselsnummer aldri i URL eller logg (personopplysningsloven § 12). Alle ressurser adresseres med UUID.
- Kallerens input gir aldri 5xx (konvensjon fra arkitekturen).
- Logger viser bare sti uten spørrestreng, og aldri request-kropp.

## Akseptansekriterier

1. `GET /api/arbeidsgivere/{id}` med gyldig sesjon og rolle gir 200 med `{ data: {...} }`; uten sesjon 401; med rolle hos annen arbeidsgiver 404.
2. `GET /api/arbeidsgivere/ikke-en-uuid` gir 400 Problem Details med `errors.id`, ikke 500.
3. En kastet `InvalidOperationException` i et testendepunkt gir 500 med `traceId` i kroppen og samme `traceId` i loggen, og ingen stakksporing i kroppen.
4. OpenAPI-dokumentet valideres som gyldig 3.1 i CI, og `web/src/api/openapi.json` er identisk med det genererte (CI feiler ellers).
5. `pnpm run api:generate` i `web/` gir en `client.ts` som kompilerer med `tsc --noEmit`, og typen for `arbeidsgiver.organisasjonsnummer` er `string`.
6. `decimal`-felt serialiseres som `12345.00` (tall), `DateOnly` som `"2026-03-15"`, og `YearMonth` som `"2026-03"`.
7. `/health` svarer 200 uten database; `/health/ready` svarer 503 når databasen er nede.
8. Loggen for et kall til `/api/arbeidsgivere/{id}?debug=1` inneholder stien men ikke `debug=1`.

## Tester

- `tests/Lonn.Api.Tests/` med `WebApplicationFactory` mot Testcontainers-Postgres: alle kriteriene over.
- Snapshot-test (Verify) av OpenAPI-dokumentet.

## Åpne spørsmål

- Ingen juridiske. Teknisk valg mellom FluentValidation og DataAnnotations tas i pakken og dokumenteres i en kort ADR.
